== Managing Images
By the end of this exercise, you should be able to:

* Rename and retag an image
* Push and pull images from the public registry
* Delete image tags and image layers, and understand the difference between the two operations

=== Tagging and Listing Images
Download the `alpine:3.20` image from Docker Hub:

[source,shell]
----
[user@node ~]$ docker image pull alpine:3.20
----
Make a new tag of this image:

[source,shell]
----
[user@node ~]$ docker image tag alpine:3.20 my-alpine:dev
----
NOTE: No new image has been created; `my-alpine:dev` is just a pointer to the same image as `alpine:3.20`.

List your images:

[source,shell]
----
[user@node ~]$ docker image ls
----
You should have `alpine:3.20` and `my-alpine:dev` both listed, and they should have the same image ID since they are the same image.

=== Making an Account on Docker's Hosted Registry
GitHub includes a free Container Registry that anyone with a GitHub account can use.

All you need is a Personal Access Token (PAT), which can be created here: https://github.com/settings/tokens

Required permission: write:packages

=== Sharing Images

Push your image:

[source,shell]
----
[user@node ~]$ docker image push my-alpine:dev
----
You should get a denied: requested access to the resource is denied error.

Login by doing `docker login`, and try pushing again. 
[source,shell]
----
[user@node ~]$ PAT_CR=<YOUR_PERSONAL_ACCESS_TOKEN>
[user@node ~]$ echo $PAT_CR | docker login ghcr.io -u [GITHUB_USERNAME] --password-stdin
[user@node ~]$ docker image push my-alpine:dev
----

The push fails again because we haven't namespaced our image correctly; we also have to specify the registry when not pushing to Dockerhub: `ghcr.io/<GITHUB_USERNAME>/<IMAGE_NAME>[:<optional tag>]`.

Retag your image to be namespaced properly, and push again:

[source,shell]
----
[user@node ~]$ docker image tag my-alpine:dev ghcr.io/[GITHUB_USERNAME]/my-alpine:dev
[user@node ~]$ docker image push ghcr.io/[GITHUB_USERNAME]/my-alpine:dev
----
Go to your GitHub Packages page. You should see our image my-alpine listed there. Click on it to view the details. Go to the package settings and change the default visibility to public.

Next, write a `Dockerfile` that uses `ghcr.io/[GITHUB_USERNAME]/my-alpine:dev` as its base image, and installs any application you like on top of that. Build the image, and simultaneously tag it as `:1.0`:

[source,shell]
----
[user@node ~]$ docker image build -t ghcr.io/[GITHUB_USERNAME]/my-alpine:1.0 .
----
Push your `:1.0` tag to ghcr.io, and confirm you can see it in the appropriate repository.

Finally, list the images currently on your node with docker image ls. You should still have the version of your image that wasn't namespaced with your Github user name; delete this using `docker image rm`:

[source,shell]
----
[user@node ~]$ docker image rm my-alpine:dev
----
Only the tag gets deleted, not the actual image. The image layers are still referenced by another tag.

=== Conclusion
In this exercise, we practiced tagging images and exchanging them on the public registry. The namespacing rules for images on registries are mandatory: user-generated images to be exchanged on the public registry must be named like `ghcr.io/<GITHUB_USERNAME>/<IMAGE_NAME>[:<optional tag>]`; official images in the Docker registry just have the repo name and tag.

NOTE: Also note that as we saw when building images, image names and tags are just pointers; deleting an image with `docker image rm` just deletes that pointer if the corresponding image layers are still being referenced by another such pointer. Only when the last pointer is deleted are the image layers actually destroyed by docker image rm.
