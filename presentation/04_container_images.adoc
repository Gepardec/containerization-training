== Container images

[.notes]
--
* In previous modules we focused on process isolation.
* For real portability, the process needs a portable filesystem, runtime, and dependencies.
* In this module, we focus on image internals and practical image construction for modern CI/CD.
--

=== Learning objectives

By the end of this module, trainees will be able to:

* Explain image layers, copy-on-write, and the writable container layer
* Build reproducible images with Dockerfiles / Containerfiles
* Use cache-aware build patterns for faster iteration
* Apply production-ready image practices for security and operability
* Correctly tag, namespace, and publish images to registries

[.columns.image-text-balance]
=== What are container images?

[.column.image-text]
* A container image is a packaged filesystem plus metadata
* Built from a stack of immutable layers
* Starts from a base image
* Each build instruction can create a new layer

[.column.image-visual]
image::04_container_images/image-layered-fs.svg[width=100%]

[.notes]
--
* Layers are additive snapshots of filesystem changes and metadata.
* The image stack usually starts with a base OS/runtime layer.
* Higher layers override files with the same path from lower layers.
--

=== Sharing layers

image::04_container_images/image-shared-layers.svg[]

[.notes]
--
Benefits of layering:

* Shared layers reduce disk and memory usage
* Downloads are deduplicated by content digest
* Build cache can reuse unchanged layers
--

=== The writable container layer

image::04_container_images/image-container-layer.svg[]

[.notes]
--
* Starting a container adds a thin writable layer on top of image layers.
* Image layers remain read-only.
* Changes made by the running container are written only to the writable layer.
* If a file from a lower layer is modified, copy-on-write creates a copy in the writable layer.
--

=== Images: copy on write

image::04_container_images/image-copy-on-write.svg[]

[.notes]
--
* Copy-on-write means only changed files are copied into a new upper layer.
* Effective file content is resolved from top-most matching path in the layer stack.
--

=== Linux containers: Union FS

image::04_container_images/image-union-fs.svg[]

[.notes]
--
* Linux engines compose layers with a union filesystem (for example, overlay-based drivers).
* The merged mount appears as one filesystem view inside the container.
--

=== Creating images

Three common methods:

* Build from a Dockerfile / Containerfile (recommended)
* Commit a running container (`docker container commit`) for quick experimentation only
* Import a tarball as a base image (`docker image import`) for special cases

=== Committing container changes

* `docker container commit` stores current writable layer as a new image layer
* Pro: quick for interactive exploration
* Con: difficult to audit, reproduce, and automate
* Guidance: avoid for production pipelines

=== Dockerfiles / Containerfiles

* Machine-readable build recipe
* Documents image construction step-by-step
* Enables CI/CD automation and repeatability
* `FROM` defines the base image
* `RUN`, `COPY`, `ADD`, `ENV`, and others define layers/metadata

[source,Dockerfile]
----
# Comments start with '#'
FROM ubuntu:24.04
RUN apt-get update && apt-get install -y --no-install-recommends wget \
    && rm -rf /var/lib/apt/lists/*
COPY data /myapp/data
----

[.notes]
--
* Dockerfile and Containerfile are equivalent formats in common engines.
* In this training we use the term Dockerfile for familiarity.
--

=== Build cache fundamentals

image::04_container_images/image-build-cache.svg[width=20%]

Cache reuse depends on:

* The instruction itself
* Build arguments and environment that affect the instruction
* Files from the build context used by that instruction
* The parent layer digest

[.notes]
--
* Once cache is invalidated at one step, subsequent steps usually rebuild.
* Cache behavior is deterministic and digest-based.

The instruction itself
If the command text changes, cache is invalid.
Example: changing RUN apk add wget to RUN apk add wget curl creates a different fingerprint.

Build arguments and environment that affect the instruction
If ARG/ENV values used by that step change, cache is invalid.
Example: ARG APP_VERSION=1.0 to 1.1, and a RUN that uses APP_VERSION.

Files from the build context used by that instruction
For COPY/ADD (and anything depending on copied files), Docker hashes file contents/metadata.
If those files change, cache is invalid.
Example: changing package.json invalidates COPY package.json and usually the following dependency install step.

The parent layer digest
Each step builds on the previous step’s result.
If an earlier layer changed, its digest changes, so later steps usually cannot reuse cache even if their own text is unchanged.

Practical rule:

Change early step -> many later steps rebuild.
Keep stable/heavy steps early (only if inputs rarely change).
Copy dependency manifests first, install deps, then copy app source.
That layout gives much better cache reuse during normal development.
--

=== CMD and ENTRYPOINT

* Every container runs a PID 1 process
* `ENTRYPOINT` defines the executable
* `CMD` defines default arguments (or default command if no ENTRYPOINT)
* Runtime command can override `CMD`
* `--entrypoint` can override `ENTRYPOINT`

[.notes]
--
Recommended pattern:

* Use exec form for `ENTRYPOINT`
* Use `CMD` for default parameters
* This preserves signal handling and predictable overrides
--

=== Shell vs exec form

[source,Dockerfile]
----
# Shell form (runs via /bin/sh -c)
CMD java -jar /app/app.jar

# Exec form (preferred for ENTRYPOINT/CMD in production)
ENTRYPOINT ["java", "-jar", "/app/app.jar"]
CMD ["--server.port=8080"]
----

[.notes]
--
* Shell form enables shell expansion but introduces an extra shell process.
* Exec form is JSON array syntax and avoids shell interpretation.
--

=== COPY and ADD

`COPY` is the default choice for local files.

[source,Dockerfile]
----
COPY <src> <dest>
----

Use `ADD` only when you explicitly need:

* Auto-extracting local tar archives
* Fetching from URL sources (if policy allows)

[.notes]
--
* Prefer `COPY` for clarity and least surprise.
* File content checksums participate in cache invalidation.
--

=== Build context and .dockerignore

`.dockerignore` is critical for fast and safe builds.

Benefits:

* Reduces build context transfer size
* Prevents accidental inclusion of secrets and local artifacts
* Improves cache stability

Example:

[source,text]
----
.git
node_modules
*.log
.env
target
dist
----

[.notes]
---
.dockerignore improves cache stability because it keeps noisy files out of the build context hash.

When Docker evaluates cache for steps like COPY . ., it fingerprints the files that are sent as build context.
If that context includes frequently changing files (logs, temp files, .git, build artifacts), the fingerprint changes all the time, and cache gets invalidated even though your real app inputs did not change.

With .dockerignore:

those irrelevant files are excluded from context
fewer accidental hash changes happen
COPY and downstream layers keep hitting cache more consistently
Simple example:

Without .dockerignore: updating app.log can invalidate COPY . . and force dependency/install steps to rebuild.
With .dockerignore containing *.log: changing app.log does not affect context hash, so cache can still be reused.
So “cache stability” means: same meaningful inputs -> same cache result, with less random cache busting from unrelated files.
---

=== Dockerfile command roundup

* `FROM`: base image
* `RUN`: execute build-time commands
* `COPY`: copy files into image
* `ADD`: specialized copy behavior
* `ENTRYPOINT` and `CMD`: default runtime behavior
* `USER`: set runtime user
* `HEALTHCHECK`: define container health probe

=== Advanced image construction goals

Build images that are:

* Lightweight
* Secure
* Fast to build
* Easy to operate and debug

=== The scratch image

* Special empty base image
* Not pulled from a registry
* Useful for minimal final images
* Common in multi-stage builds

[source,Dockerfile]
----
FROM scratch
COPY hello /hello
ENTRYPOINT ["/hello"]
----

[.notes]
--
* `scratch` is typically used for static binaries or fully self-contained artifacts.
--

=== Multi-stage builds (1/2)

Naive single-stage C build:

[source,Dockerfile]
----
FROM alpine:3.20
RUN apk add --no-cache build-base
WORKDIR /app
COPY hello.c /app
RUN gcc -Wall hello.c -o /app/hello
CMD ["/app/hello"]
----

[.notes]
--
* This works, but final image includes compiler toolchain.
--

=== Multi-stage builds (2/2)

Improved multi-stage build:

[source,Dockerfile]
----
# Build stage
FROM alpine:3.20 AS build
RUN apk add --no-cache build-base
WORKDIR /src
COPY hello.c .
RUN gcc -Wall hello.c -o /out/hello

# Runtime stage
FROM alpine:3.20
COPY --from=build /out/hello /app/hello
ENTRYPOINT ["/app/hello"]
----

[.notes]
--
* Final image contains only the runtime artifact.
* Smaller attack surface and faster pull/start times.
--

=== Build targets

Use named stages and optional build target selection.

[source,Dockerfile]
----
FROM base-image AS base
# ...

FROM toolchain-image AS test
# ...

FROM runtime-image
COPY --from=test /out/app /app/app
----

[source,shell]
----
# Build final image (last stage)
docker image build -t myapp:1.0 .

# Build an intermediate stage by name
docker image build --target test -t myapp:test .
----

=== Security baseline for Dockerfiles

* Start from trusted, maintained base images
* Prefer minimal runtime images
* Run as non-root user (`USER`)
* Avoid embedding secrets in image layers
* Keep package lists/caches out of final image

Example:

[source,Dockerfile]
----
FROM node:22-bookworm-slim
WORKDIR /app
COPY package*.json ./
RUN npm ci --omit=dev
COPY . .
RUN useradd -r -u 10001 appuser && chown -R appuser:appuser /app
USER appuser
CMD ["node", "server.js"]
----

=== Build-time secrets with BuildKit

Never pass secrets via `ARG` or `ENV` during build.

[source,Dockerfile]
----
# syntax=docker/dockerfile:1.7
FROM alpine:3.20
RUN --mount=type=secret,id=npm_token \
    sh -c 'echo "Using secret at /run/secrets/npm_token"'
----

[source,shell]
----
docker image build \
  --secret id=npm_token,src=$HOME/.npm-token \
  -t myapp:secure .
----

=== HEALTHCHECK and operability

`HEALTHCHECK` lets orchestrators detect unhealthy containers.

[source,Dockerfile]
----
HEALTHCHECK --interval=30s --timeout=3s --start-period=10s --retries=3 \
  CMD wget -qO- http://localhost:8080/health || exit 1
----

Guidance:

* Keep checks lightweight
* Verify critical readiness path
* Log to stdout/stderr for observability

=== Development vs production layering

Cache-aware development pattern:

[source,Dockerfile]
----
FROM python:3.12-slim
WORKDIR /app
# Copying dependency manifests first avoids re-installing dependencies on every code change.
COPY requirements.txt ./
RUN pip install --no-cache-dir -r requirements.txt
COPY . .
CMD ["python", "main.py"]
----

[.notes]
--
* Copying dependency manifests first avoids re-installing dependencies on every code change.
--

=== Updates and patching strategy

* Rebuild from Dockerfile when dependencies or base image change
* Avoid layering ad-hoc patch commands over outdated images
* Prefer immutable references in CI (`image@sha256:...`) for reproducibility

=== Image tags and digests

* Tags are mutable pointers (`myapp:1.2.3`, `myapp:latest`)
* Digests are immutable content addresses (`myapp@sha256:...`)
* Recommended: publish semantic version tags plus immutable digest references

[source,shell]
----
# Tag examples
docker image build -t myorg/myapp:1.2.3 -t myorg/myapp:latest .

# Pull immutable image by digest
docker image pull myorg/myapp@sha256:abc123...
----

=== Image namespaces

Images can be addressed as:

* Root namespace (`nginx`, `redis`) on default registries
* User/org namespace (`myorg/myapp:1.2.3`)
* Fully qualified registry path (`registry.example.com/myorg/myapp:1.2.3`)

=== Multi-platform builds (buildx)

Modern teams often publish for multiple architectures.

[source,shell]
----
# Example: build and push amd64 + arm64
docker buildx build \
  --platform linux/amd64,linux/arm64 \
  -t registry.example.com/myorg/myapp:1.2.3 \
  --push .
----

=== Vulnerability scanning in CI/CD

Integrate image scanning before deployment.

Example tools:

* Docker Scout
* Trivy
* Grype

[.notes]
--
* Scan both OS and application dependencies.
* Treat high/critical findings with policy gates.
--

=== Sharing container images

Typical workflow:

* Build image locally or in CI
* Tag with namespace and version
* Authenticate to registry
* Push image
* Deploy by version tag and/or digest

[source,shell]
----
docker image tag myapp:1.2.3 registry.example.com/team/myapp:1.2.3
docker image push registry.example.com/team/myapp:1.2.3
----

=== Production-ready Dockerfile checklist

* Use a maintained base image (pin digest when needed)
* Keep build context small with `.dockerignore`
* Use multi-stage builds to remove compilers/SDKs from runtime
* Run as non-root with `USER`
* Keep secrets out of layers (BuildKit secrets)
* Add `HEALTHCHECK` when meaningful
* Scan images in CI/CD
* Tag consistently (`version`, `git-sha`, optional `latest`)

=== Container image takeaways

* Container images are built from read-only layers plus metadata.
* Dockerfiles provide reproducible, auditable image builds.
* Layering and cache strategy strongly affect developer feedback cycle.
* Security and operability practices are required for production images.
* Tags are mutable references; digests are immutable content addresses.
